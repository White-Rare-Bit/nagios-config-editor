Frontend Architecture

The frontend is vanilla JavaScript with no build system, no framework, and no bundler. All modules use the IIFE (Immediately Invoked Function Expression) pattern. Explorer modules attach to the window.Explorer namespace; core modules are standalone globals.

Core Modules

These modules are loaded on every page via base.html. They are loaded in a specific order so that each module can rely on the ones before it:

Module Responsibility
api-client.js Fetch wrapper with staging headers; all API calls return {success, data, error}
base-state.js Shared state (lock status, session info) accessible from any module
session-manager.js Session ID generation and user identity management
ui-notifications.js Toast notifications, flash messages
git-ui.js Git result panel UI (terminal-style output)
commit-dialog.js Commit overlay, staged changes display, diff viewer
lock-manager.js Staging lock polling and lock banner display
base.js Initialization, event delegation, keyboard shortcuts, DebugLogger

Explorer Component Architecture

The Object Explorer (/explorer) is the most complex page, with 16 modules in the Explorer namespace. All modules attach to window.Explorer and share state via Explorer.state.

Event Delegation

Instead of attaching event listeners to individual elements, the frontend uses event delegation via data-action attributes. When a user clicks an element, the click bubbles up to a parent handler that reads the data-action attribute and dispatches to the matching function in an actionHandlers map: 

// HTML
<button data-action="deleteObject" data-index="42">Delete</button>

// JavaScript
const actionHandlers = {
    deleteObject: (el) => {
        const index = el.dataset.index;
        // handle delete...
    }
};

This pattern avoids the need to re-bind listeners when the DOM is rebuilt (which happens frequently as the tree and editor re-render).

ApiClient

All API calls go through the ApiClient module, which wraps fetch() and normalizes responses into a consistent format: 

const result = await ApiClient.post('/api/staging', { data: stagingData });
// result = { success: true, data: { ... } }
// or:     { success: false, error: "Description of problem" }

The ApiClient automatically attaches the X-Session-Id header to every request, which the backend uses for staging lock validation. It also handles JSON serialization and error normalization.

State Management

base-state.js provides shared state accessible from any module on any page. It holds lock status and session information. For the Explorer page, Explorer.state (defined in main.js) holds the full application state including:

  • allObjects — All parsed Nagios objects
  • selections — Currently selected objects in the tree
  • Staging maps — Pending edits, staged moves, creations, deletions
  • Undo stack — Local undo history

State is updated in response to API calls and user interactions. When staging state changes, the Explorer calls refreshAfterObjectChange() to re-render affected UI components.

Domain Metadata

All Nagios domain constants (type labels, name fields, required fields, reference fields, attributes) are defined in nagios_model.py on the backend and served via GET /api/metadata. The frontend fetches this once at startup and stores it in Explorer.constants.

Never hardcode Nagios domain metadata in JavaScript. Always read from the metadata API. To add a new object type or reference field, update nagios_model.py and the frontend picks it up automatically.

Metadata from API (source of truth)

  • typeLabels — Display names for each object type
  • nameFields — Which attribute holds the name for each type
  • REQUIRED_FIELDS — Mandatory fields per object type
  • referenceFields — Fields that reference other objects
  • ATTR_REFERENCE_MAP — Maps attributes to referenced object types
  • NAGIOS_ATTRIBUTES — All known attributes per object type
  • defaultAttributes — Default attribute sets for new objects
  • groupStructure — Group membership relationships

Hardcoded Constants (UI-only)

A small number of UI-only constants are hardcoded in constants.js because they have no backend equivalent:

  • identityFields — Fields that identify an object (for display)
  • inheritanceAttrs — Attributes related to template inheritance
  • referenceAttrs — Attributes that reference other objects (for UI highlighting)

CSS Architecture

Styles use a design token system with CSS custom properties. All tokens are defined in tokens.css with the --nbe- prefix:

  • Light theme — --nbe-{category}-{variant}
  • Dark theme — --nbe-dark-{category}-{variant} (Explorer page only)
  • Categories — bg, text, border, accent, input, btn, tab, validation

Component styles are in separate CSS files per page. The button system uses .nbe-btn as the base class with modifier classes like --primary, --danger, --ghost, and size modifiers like --xs, --sm.

Typography tokens provide semantic groups (h1, h2, body, code, etc.) each with -size, -weight, and -line-height variants. Fonts are Inter (sans-serif) and JetBrains Mono (monospace), bundled as woff2 files.
