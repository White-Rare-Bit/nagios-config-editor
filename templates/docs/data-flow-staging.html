This page describes the internal mechanics of the shadow copy system: how edits flow from the UI to disk, the shadow copy lifecycle, how objects are identified via stable keys, the file-level undo mechanism, and the apply/destroy process.

Edit Flow

When a user makes a change in the UI, it follows this path:

  1. UI input — User edits an attribute, moves an object, creates a file, etc.
  2. API call — Frontend sends the change to the backend via ApiClient.post() with the X-Session-Id header. The route handler calls ensure_shadow_lock() to create the shadow (if needed) and verify lock ownership, then takes a file-level snapshot for undo.
  3. NagiosService — The service writes changes directly to the shadow copy's .cfg files via the parser and writer.
  4. Shadow files — The shadow .cfg files now contain the updated configuration. The service reloads to reflect the new state.
  5. Commit dialog — User reviews unified diffs (shadow vs original) for every modified file.
  6. Apply — The shadow copy replaces the original config directory. A backup is created first.
  7. Git commit — Optionally, changes are committed to version control.
The critical point: steps 1 through 4 modify only the shadow copy. Your original .cfg files are only replaced during step 6 (Apply).

Shadow Copy Lifecycle

The shadow copy has two states:

  • NO SHADOW — No shadow copy exists. The app reads from the original config. Any session can start editing.
  • SHADOW ACTIVE — A shadow copy exists, owned by a session. The app reads from and writes to the shadow. All mutations modify shadow files directly.

Transitions: NO SHADOW → (first mutation creates shadow + acquires lock) → SHADOW ACTIVE → (apply replaces original, or discard/break destroys shadow) → NO SHADOW.

Stable Keys

Objects are identified by a stable key rather than their global index. A stable key has the format: 

"source_file|object_type|name"

For example: "hosts/webservers.cfg|host|webserver01"

Stable keys survive parser reloads. When the parser re-reads config files (which happens after every mutation in the shadow copy), global indices change but stable keys remain the same as long as the object still exists. The frontend uses stable keys for all API calls. 

# Generate a stable key
stable_key = generate_stable_key(obj.source_file, obj.object_type, obj.get_name())

# Look up an object by stable key
idx, obj = service.find_object_by_stable_key(stable_key)

File-Level Undo Snapshots

Before each mutation, the route handler snapshots the affected files within the shadow copy. Snapshots are stored as a LIFO stack: 

# Route handler pattern
sm = get_shadow_manager()
rel_path = os.path.relpath(obj.source_file, sm._config_dir)
sm.snapshot_files([rel_path], "edit host webserver01")

# Then perform the actual mutation
service.update_object(...)

Each snapshot entry records:

  • The relative paths of affected files
  • The content of those files before the mutation
  • A human-readable description (e.g., "edit host webserver01")

When POST /api/staging/undo is called, the top snapshot is popped and the affected files are restored to their pre-mutation state. The service is then reloaded to reflect the reverted configuration.

File-level snapshots are more robust than operation-level undo. They correctly handle edge cases like operations that affect multiple objects within the same file, because the entire file state is captured and restored.

Shadow Copy Manager

The ShadowCopyManager class manages the shadow copy lifecycle:

Method What It Does
create_shadow(session_id) Copies original config to shadow directory, acquires session lock
has_shadow() Returns whether a shadow copy currently exists
can_modify(session_id) Checks if the given session owns the lock
snapshot_files(rel_paths, desc) Captures file contents for undo before a mutation
undo() Restores files from the most recent snapshot
get_shadow_diff() Returns unified diffs for all modified files (shadow vs original)
apply_shadow() Replaces original config with shadow, creates backup first
destroy_shadow() Deletes shadow copy, releases lock, discards all changes

Lock Mechanics

The shadow copy uses session-based locking to prevent concurrent editing:

  • Auto-acquire — The first mutation by a session creates the shadow copy and acquires the lock. The session ID is sent via the X-Session-Id header.
  • Validation — Every mutation route calls ensure_shadow_lock(session_id) which returns a 423 error if a different session owns the lock.
  • Release — The lock is released when the shadow is applied or destroyed.
  • Break lock — An admin can force-break a stale lock via POST /api/staging/break-lock, which destroys the shadow copy and discards all pending changes.
# Route handler pattern for mutations
session_id = request.headers.get("X-Session-Id")
success, error = ensure_shadow_lock(session_id)
if not success:
    return error  # 423 if locked by another session

Apply Process

When POST /api/staging/apply is called:

  1. Backup — A zip backup of the original config is created via BackupManager.create_backup("pre_apply")
  2. Replace — The shadow directory's contents replace the original config directory
  3. Reload — NagiosService reloads the configuration from the (now updated) original directory
  4. Cleanup — The shadow copy is destroyed and the lock is released
The apply is all-or-nothing. Either the entire shadow copy replaces the original, or nothing changes. There are no partial applies or multi-phase write sequences.

Commit Workflow

The full commit workflow combines applying the shadow copy with a Git commit:

  1. User clicks the Commit button in the navbar
  2. Frontend fetches GET /api/staging/info for change counts and GET /api/staging/diff for unified diffs
  3. Commit dialog renders per-file unified diffs
  4. User enters a commit message
  5. POST /api/staging/apply replaces the original config with the shadow
  6. POST /api/git/commit stages and commits the changes
  7. Git result panel shows the outcome (terminal-style)
  8. Page reloads to reflect the new state

Atomic File Writes

All file writes by NagiosService (both to shadow and original) use an atomic write pattern to prevent data corruption: 

# 1. Write to a temp file in the same directory
fd, temp_path = tempfile.mkstemp(suffix='.tmp', prefix='.nagios_', dir=dir_path)

# 2. Write content, flush, and fsync
with os.fdopen(fd, 'w', encoding='utf-8') as f:
    f.write(content)
    f.flush()
    os.fsync(f.fileno())

# 3. Atomic rename (POSIX guarantee)
os.replace(temp_path, filepath)

This ensures that a crash or power failure during a write never leaves a file in a partially written state. The file is either fully written or untouched.
