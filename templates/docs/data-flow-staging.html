This page describes the internal mechanics of the staging system: how edits flow from the UI to disk, how objects are identified, the structure of staged operations, lock management, the undo stack, the 10-phase apply process, and conflict detection.

Edit Flow

When a user makes a change in the UI, it follows this path:

  1. UI input — User edits an attribute, moves an object, creates a file, etc.
  2. API call — Frontend sends the change to the backend via ApiClient.post() with the X-Session-Id header
  3. StagingManager — Backend validates the session lock, then stores the operation in staging state
  4. staging.json — The staging data is persisted atomically to disk (temp file + os.replace())
  5. Commit dialog — User reviews all staged changes as diffs
  6. Apply — All staged changes are written to the actual config files in a 10-phase process
  7. Git commit — Optionally, changes are committed to version control
The critical point: steps 1 through 4 never modify your Nagios config files. The actual .cfg files are only written during step 6 (Apply).

State Transitions

The staging system has three states:

  • EMPTY — No session owns staging. Available for acquisition by any session.
  • ACTIVE — A session holds the lock and is making edits.
  • RESTORE_PENDING — A backup restore has populated staging, awaiting apply or discard.

Transitions: EMPTY → (first edit) → ACTIVE → (apply or clear) → EMPTY. A backup restore creates the RESTORE_PENDING state, which transitions back to EMPTY after the user applies or discards the restore. See Staging System for the user-facing workflow.

Stable Keys

Objects are identified by a stable key rather than their global index. A stable key has the format: 

"source_file|object_type|name"

For example: "hosts/webservers.cfg|host|webserver01"

Stable keys survive parser reloads. When the parser re-reads config files (which happens after every apply), global indices change but stable keys remain the same as long as the object still exists at the same location. This is essential for the staging system, which must track objects across reloads. 

# Generate a stable key
stable_key = generate_stable_key(obj.source_file, obj.object_type, obj.get_name())

# Look up an object by stable key
idx, obj = service.find_object_by_stable_key(stable_key)

Staged Operations

All pending changes are stored in staging.json under the following fields:

Field Operation What It Stores
pendingEdits Object edits Original + edited attribute dictionaries, keyed by stable key
stagedMoves Object moves Source file, target file, insert position
stagedCreations Object creations Object type, attributes, target file
stagedObjectDeletions Object deletions Source file, line number of the object to delete
stagedFileCreations File creations Path of new .cfg file to create
stagedFileDeletions File deletions Path of file to delete
stagedFileMoves File moves Source path, target path
stagedFolderCreations Folder creations Path of new folder to create
stagedFolderDeletions Folder deletions Path of folder to delete recursively
stagedFolderMoves Folder moves Source path, target path

Lock Mechanics

The staging system uses session-based locking to prevent concurrent editing:

  • Auto-acquire — The first edit by a session automatically acquires the lock. The session ID is sent via the X-Session-Id header.
  • Validation — Every staging mutation calls sm.can_modify(session_id) to verify the requesting session owns the lock.
  • Release — The lock is released when staging is applied or cleared.
  • Break lock — An admin can force-break a stale lock via POST /api/staging/lock/break, which discards the other session's staged changes.
# Route handler pattern for staging mutations
if not sm.can_modify(request.headers.get('X-Session-Id')):
    return jsonify({'error': 'Locked by another user', 'locked': True}), 423

Undo Stack

Every staging operation pushes an entry onto a LIFO undo stack. Each entry contains the inverse operation needed to undo the change: 

{
    "id": "a1b2c3d4",
    "type": "edit",
    "data": { ... operation-specific inverse data ... },
    "description": "Edit host 'webserver01'",
    "timestamp": 1707500000.0
}

Undo types include: edit, move, creation, deletion, file_create, file_delete, file_move, folder_create, folder_delete, and folder_move.

The staging_manager.py module maintains a registry of undo handlers (UNDO_HANDLERS) that maps each operation type to the function that reverses it. When POST /api/staging/undo is called, the top entry is popped and its corresponding handler is invoked.

Apply Phase Order

When POST /api/staging/apply is called, all staged changes are written to disk in a carefully ordered 10-phase process. The order prevents conflicts — for example, folders must be created before files can be placed in them, and objects must be deleted before the files containing them are removed.

  1. Folder creations — Create new folders, sorted parent-first so parent directories exist before child directories
  2. File creations — Create new .cfg files
  3. Object deletions — Delete objects in reverse line order per file (so line numbers of earlier objects remain valid)
  4. Object moves — Move objects between files using file-based rewrite, computing final positions
  5. Object edits — Surgical replace of attribute blocks within files
  6. Object creations — Append new objects to their target files
  7. File moves — Rename or relocate files
  8. Folder moves — Rename or relocate folders
  9. File deletions — Delete files from disk
  10. Folder deletions — Delete folders, sorted child-first so empty folders are removed before their parents

Each phase is implemented as a method on NagiosService: apply_folder_creations(), apply_file_creations(), etc. The is_safe callback is passed to file/folder phases to validate path safety before each operation.

Before the apply process begins, the backend creates an automatic backup via BackupManager.create_backup("pre_apply"). If anything goes wrong, you can restore from the Backups page.

Conflict Detection

The staging system tracks file checksums to detect external modifications:

  1. When a file is first edited, its SHA256 checksum is captured as a base checksum via sm.update_base_checksums([file_path])
  2. Before applying, sm.detect_conflicts() recomputes the current checksum of each file and compares it to the base
  3. If any file's checksum has changed (meaning it was modified outside the app), the apply is blocked with a 409 status

This prevents the apply process from silently overwriting changes made by another user, tool, or manual edit.

Commit Workflow

The full commit workflow combines applying staged changes with a Git commit:

  1. User clicks the Commit button in the navbar
  2. Frontend fetches /api/staging/diff and /api/staging/analyze-references
  3. Commit dialog renders file-based change diffs
  4. User enters a commit message and optionally checks "Update references"
  5. POST /api/staging/apply writes changes to disk (with optional reference updates)
  6. POST /api/git/commit stages and commits the changes
  7. Git result panel shows the outcome (terminal-style)
  8. Staging is cleared, page reloads to reflect the new state

Atomic File Writes

All file writes during the apply phase (and staging persistence) use an atomic write pattern to prevent data corruption: 

# 1. Write to a temp file in the same directory
fd, temp_path = tempfile.mkstemp(suffix='.tmp', prefix='.nagios_', dir=dir_path)

# 2. Write content, flush, and fsync
with os.fdopen(fd, 'w', encoding='utf-8') as f:
    f.write(content)
    f.flush()
    os.fsync(f.fileno())

# 3. Atomic rename (POSIX guarantee)
os.replace(temp_path, filepath)

This ensures that a crash or power failure during a write never leaves a file in a partially written state. The file is either fully written or untouched.
