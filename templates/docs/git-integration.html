Git Integration

On this page
  • Git page layout: Changes and History tabs
  • Commit workflow with staging integration
  • Discarding changes and restoring commits
  • Wiping git history

Nagios Bulk Editor includes built-in Git version control. Every set of changes you apply can be committed to a local Git repository, giving you a full audit trail and the ability to restore any previous configuration state.

Git operations require your configuration directory to be (or become) a Git repository. If it is not already initialized, the editor will offer to run git init automatically when you make your first commit.

The Git Page

Navigate to the Git page from the main navbar. The page has two tabs:

  • Changes — shows uncommitted file changes and staged (pending) editor changes.
  • History — shows the commit log with date, author, message, and a Restore button for each commit.

The sidebar displays the current branch name and a summary of how many files have uncommitted changes. If the directory is not a Git repository, a message explains how to initialize one.

Setting Up Your Identity

Before you can commit, Git needs to know your name and email. Nagios Bulk Editor stores this in your browser's localStorage, so each user has their own identity.

  1. Go to Settings from the navbar.
  2. Enter your Name and Email in the Git Identity section.
  3. Click Save. Your identity is stored locally and sent with every commit.

If you try to commit without a configured identity, the commit dialog shows a warning with a link to the Settings page.

Viewing Changes

The Changes tab shows two types of information:

Pending Staged Changes

If you have edits in the staging area that have not been applied yet, a Pending Staged Changes panel appears at the top. It lists all staged operations (edits, moves, creations, deletions, file operations) with a count. Click Review & Commit to open the commit dialog directly.

File Diffs

Below the staging preview, a two-panel layout shows the list of changed files on the left and a diff viewer on the right. Click any file to see its diff.

  • Lines added are shown in green.
  • Lines removed are shown in red.
  • Each file has a status badge: M (modified), A (added), D (deleted), ?? (untracked).

Committing Changes

The commit workflow brings together the staging system and Git:

  1. Make your edits in the Object Explorer (they go into staging).
  2. Click the Commit button in the navbar. This opens the commit dialog.
  3. Review the changes. The dialog shows a per-file diff of every object that will be modified, created, moved, or deleted. Use the Context slider to control how many surrounding lines appear in diffs.
  4. Enter a commit message in the text area at the bottom.
  5. Click Apply Changes. This does two things in sequence:
    • Writes all staged changes to disk (the "apply" step).
    • Runs git add -A && git commit with your message and identity.
  6. A terminal-style result panel shows the exact Git command that ran, whether it succeeded or failed, and the commit hash on success.
If the Git commit fails after the apply step, your staged changes are preserved and the result panel offers a Retry Commit button. You can also choose to Discard Staging if you want to abandon the commit (the files on disk will still reflect the applied changes).

Git-Only Commits

If files were changed outside the editor (for example, by editing them manually on the server), the commit dialog detects these external changes and shows their diffs in a separate section. You can commit them the same way — just enter a message and click Apply.

Discarding Changes

There are several ways to discard changes:

Action Where What It Does
Discard file Changes tab — click Discard next to a file Runs git checkout -- <file> to restore that one file to its last committed state.
Discard All Commit dialog — click Discard All If only staged changes exist, clears the staging area. If there are git changes, runs git checkout -- . and git clean -fd to restore the entire working directory.
Discarding file changes via Git is irreversible. The file is restored to its last committed state and any uncommitted modifications are lost.

Commit History

The History tab shows a paginated table of past commits. Each row displays:

  • Date/Time — when the commit was made.
  • Commit hash — the short SHA. The current commit is labeled with a Current badge.
  • Message — the commit message.
  • Author — who made the commit.
  • Actions — a Restore button (except for the current commit).

Columns are sortable — click a column header to sort ascending or descending. The page size defaults to 25 commits and can be changed with the pagination controls.

Restoring to a Previous Commit

Click the Restore button on any history row to roll the working directory back to that commit's state. A confirmation dialog warns that current files will be overwritten.

  • If there are uncommitted changes, they are automatically stashed before the restore.
  • Files that exist in the current state but not in the target commit are deleted.
  • After restoring, the configuration is reloaded so the Object Explorer reflects the restored state.
  • The restored state shows up as uncommitted changes, which you can then commit with a new message (e.g., "Restore to commit abc1234").

Wiping Git History

The History tab sidebar includes a Wipe Git Log button that removes all commit history and reinitializes the repository with a single fresh "Initial commit". This is useful if you want to start clean after importing a configuration.

Wiping git history is irreversible. All previous commits are permanently deleted. The current file contents are preserved as the new initial commit.
