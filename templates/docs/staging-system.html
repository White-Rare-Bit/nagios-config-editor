Shadow Copy System

On this page

  • Reviewing diffs before applying
  • Undo, apply, and discard

The shadow copy system is a core feature of Nagios Bulk Editor. When you make your first edit, a full copy of your config directory is created. All changes are made to this shadow copy — your original files are untouched until you click Apply.

How It Works

Unlike traditional staging systems that track individual operations as JSON diffs, the shadow copy system works at the filesystem level:

  1. First edit — When you make your first change, the entire config directory is copied to a temporary shadow location. The app switches to working on this copy.
  2. Subsequent edits — All further changes (object edits, moves, creations, deletions, file/folder operations) write directly to the shadow copy's .cfg files.
  3. Review — The commit dialog shows a unified diff of every file that differs between shadow and original.
  4. Apply — The shadow copy replaces the original config directory. All changes take effect at once.
  5. Discard — The shadow copy is destroyed. The original is untouched.

Staging Indicator

The Commit button in the navbar shows a count badge when there are pending changes (files that differ between shadow and original). When there are no changes, the button is grayed out.

Reviewing Changes

Click the Commit button to open the commit dialog. The dialog shows a unified diff for every modified file, with additions and deletions highlighted:

  • Modified files show inline diffs with added/removed lines highlighted.
  • New files show the entire file content as additions.
  • Deleted files show the entire file content as removals.

Click any file header in the commit dialog to expand or collapse its diff.

Undo

Before each mutation, the app takes a snapshot of the affected files. Click the Undo button in the navbar (or press Ctrl+Z / Cmd+Z) to restore the previous snapshot, reverting the most recent operation.

Undo works for all operation types: object edits, moves, creations, deletions, and file/folder operations. Each undo reverses exactly one operation by restoring the file-level snapshot.

Tip: Use Ctrl+Z (or Cmd+Z on Mac) for quick undo without clicking the button.
Undo is disabled when you are editing a text field (so it does not interfere with the browser's native text undo) and when a modal dialog is open.

Applying Changes

Click Apply in the commit dialog to replace your original config with the shadow copy. The process:

  1. An automatic backup of the original config is created
  2. The shadow copy replaces the original directory
  3. The app reloads the configuration from the new files
  4. The shadow is destroyed and the lock is released

Git Commit

If Git is configured for your Nagios config directory, the commit dialog also shows fields for a commit message, author name, and email. After applying changes, you can commit them to Git in the same step. The result is shown in a terminal-style output panel.

Lock System

The shadow copy system uses a session-based lock to prevent concurrent editing. When you make your first edit, the app creates the shadow copy and acquires the lock for your session. While you hold the lock:

  • Other users see a lock banner at the top of the page indicating that editing is locked.
  • Other users can still browse the configuration but cannot make changes.
  • The lock is released when you apply or discard all changes.
If a session holds the lock and the user is no longer active, an administrator can break the lock using the "Break Lock" button in the lock banner. Breaking the lock destroys the shadow copy and discards all pending changes.

Discarding Changes

To discard all changes, open the commit dialog and click Discard All Changes. This destroys the shadow copy entirely — your original config is restored as if no edits were made. The lock is also released, allowing other users to edit.

You can also undo individual changes using the Undo button, which restores file-level snapshots one operation at a time.

Multi-User Sync

The app periodically polls the server for status changes. If another session applies or discards changes, your view updates automatically. If the server state changes while you are browsing, the app reloads to keep your view in sync.
