Staging System

The staging system is a core feature of Nagios Bulk Editor. No changes are written to disk until you explicitly click Apply. Every edit, move, creation, and deletion is held in a staging area where you can review, undo, and refine your changes before committing them.

What Gets Staged

The staging system tracks ten distinct categories of changes:

Category Description
Object edits Attribute changes on existing objects. The original and edited values are both stored so you can see exactly what changed.
Object moves Objects moved from one file to another (via drag-and-drop or the Move dialog).
Object creations New objects added via the "+" button on file headers. Includes the object type, all attributes, and the target file.
Object deletions Existing objects staged for removal. These appear with a strikethrough in the tree.
File creations New .cfg files to be created on disk.
File deletions Existing files to be removed.
File moves Files to be renamed or relocated to a different folder.
Folder creations New directories to be created in the config tree.
Folder deletions Existing directories to be removed (along with their contents).
Folder moves Directories to be renamed or relocated.

Staging Indicator

The Commit button in the navbar shows a count badge when there are staged changes. The number reflects the total count across all categories. When there are no staged changes, the button is grayed out.

Reviewing Changes

Click the Commit button to open the commit dialog. The dialog shows a complete diff of every staged change, organized by file:

  • Object edits show inline diffs with the old and new attribute values highlighted.
  • Object moves show the source and target files.
  • Object creations show the full definition of the new object.
  • Object deletions show which objects will be removed and from which files.
  • File and folder operations show the paths involved.

Click any change header in the commit dialog to expand or collapse its diff details.

Reference Analysis

When you open the commit dialog, the app also runs a reference analysis. If any of your changes rename objects that are referenced by other objects, the dialog shows a checkbox to Update references automatically. When enabled, the apply step will update all references to renamed objects across your entire configuration.

Undo

Every staging operation is recorded on an undo stack. Click the Undo button in the navbar (or press Ctrl+Z / Cmd+Z) to undo the most recent operation. The undo button shows a tooltip with the count of operations in the stack.

Undo works for all operation types: edits, moves, creations, deletions, and file/folder operations. Each undo reverses exactly one operation.

Undo is disabled when you are editing a text field (so it does not interfere with the browser's native text undo) and when a modal dialog is open.

Applying Changes

Click Apply in the commit dialog to write all staged changes to disk. The apply process follows a specific order to avoid conflicts:

  1. Folder creations (parent folders first)
  2. File creations
  3. Object deletions (in reverse line order per file to preserve line numbers)
  4. Object moves
  5. Object edits
  6. Object creations (appended to target files)
  7. File moves
  8. Folder moves
  9. File deletions
  10. Folder deletions (child folders first)

Before writing any changes, the app creates an automatic backup of your configuration. If something goes wrong, you can restore from the Backups page (/backups).

Conflict Detection

The staging system captures file checksums when you first edit an object in a file. Before applying, it compares the current checksums against the captured ones. If a file has been modified outside the app (by another user or tool), the apply is blocked to prevent overwriting external changes.

Git Commit

If Git is configured for your Nagios config directory, the commit dialog also shows fields for a commit message, author name, and email. After applying changes to disk, you can commit them to Git in the same step. The result is shown in a terminal-style output panel.

Lock System

The staging system uses a session-based lock to prevent concurrent editing conflicts. When you make your first edit, the app automatically acquires the staging lock for your session. While you hold the lock:

  • Other users see a lock banner at the top of the page indicating that editing is locked.
  • Other users can still browse the configuration but cannot make changes.
  • The lock is released when you apply or discard all staged changes.
If a session holds the lock and the user is no longer active, an administrator can break the lock using the "Break Lock" button in the lock banner. Breaking the lock discards any staged changes from the other session.

Clearing Staging

To discard all staged changes, open the commit dialog and click Discard All Changes. This clears every pending edit, move, creation, deletion, and file/folder operation in a single action. The staging lock is also released, allowing other users to edit.

You can also discard individual changes by using Undo repeatedly, or by reverting specific attribute edits in the editor (edit the value back to its original content to remove it from staging).

Multi-User Sync

The app periodically polls the server for staging changes. If another session applies or clears staging, your view updates automatically. If the server staging state changes while you are editing, the app reloads the current staging data to keep your view in sync.
