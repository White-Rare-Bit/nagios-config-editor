Architecture

Nagios Bulk Editor is a Flask application with a vanilla JavaScript frontend. The backend is organized around an app factory pattern with dedicated service classes for each domain responsibility. There is no database — all state comes from the filesystem and in-memory staging.

App Factory

The application is created by create_app() in app.py. During initialization, all service instances are stored in app.extensions, a dictionary attached to the Flask app object. Route handlers access services through helper functions rather than importing service instances directly: 

from .helpers import get_service, get_staging_manager, get_backup_manager, get_server_config

This pattern keeps service creation centralized and makes testing easier — you can swap service instances by replacing entries in app.extensions.

Service Layer

Each backend responsibility is encapsulated in a dedicated service class:

  • NagiosService — CRUD operations on Nagios objects, apply phases, parser access
  • StagingManager — Staging state, session locks, undo stack, conflict detection
  • GitService — Git subprocess wrapper with retry logic and identity injection
  • BackupManager — Zip backup creation, restore, cleanup
  • ServerConfig — Configuration loading, saving, and environment overrides

Route handlers call service methods, receive an OperationResult, and translate it into a JSON response. Services never access Flask request/response objects directly.

OperationResult Pattern

All service methods that perform mutations return an OperationResult dataclass: 

@dataclass
class OperationResult:
    success: bool
    error: Optional[str] = None
    data: Any = None

This provides a uniform contract between service methods and route handlers. The route layer checks result.success and returns the appropriate HTTP status code: 

result = service.create_object(...)
if not result.success:
    return jsonify({'error': result.error}), 500
return jsonify({'success': True, 'data': result.data})

The operation_response() helper in routes/helpers.py automates this conversion from OperationResult to a Flask JSON response with the correct status code.

Thread Safety

Because WSGI servers may use multiple processes (not just threads), the application uses multiprocessing.Lock instead of threading.Lock for synchronization:

  • NagiosService — Lock held for all mutation operations (create, update, delete, move)
  • GitService — Lock held for multi-step mutations (add + commit must be atomic)
  • StagingManager — Uses atomic file writes (temp file + os.replace()) instead of locks
The staging system uses a session-based lock for edit ownership (only one user can edit at a time), which is separate from the process-level locks used for thread safety.

Request Lifecycle

A typical API request flows through these layers:

  1. HTTP request arrives at a Flask route handler
  2. Route handler validates input, extracts parameters, checks session lock if needed
  3. Service method performs the operation (CRUD, staging, git, etc.)
  4. OperationResult is returned from the service
  5. JSON response is sent back with the appropriate HTTP status code

For staging mutations, there is an additional lock check step: the route handler verifies that the requesting session holds the staging lock before calling the service method: 

if not sm.can_modify(request.headers.get('X-Session-Id')):
    return jsonify({'error': 'Locked by another user', 'locked': True}), 423

HTTP Status Codes

Code Meaning
200 Success
400 Invalid input (missing parameters, bad format)
404 Object or resource not found
409 Staging conflict (external file modification detected)
423 Staging locked by another session
500 Internal server error

Module Index

The backend is organized into the following modules:

Module Responsibility
app.py App factory, service initialization, extension registration
server_config.py Configuration load/save, environment variable overrides
nagios_service.py CRUD operations on objects, apply phases for staging
staging_manager.py Staging state management, session locks, undo stack
backup_manager.py Zip backup creation, restore, cleanup
nagios_parser.py Parse .cfg files into structured objects
nagios_writer.py Write .cfg files with atomic writes
nagios_model.py NagiosObject model, NAME_FIELDS, REFERENCE_FIELDS, domain constants
file_operations.py Atomic file operations, path safety validation
git_service.py Git subprocess wrapper, retry logic, identity injection
validator.py Run nagios -v validation
operation_logger.py Structured JSON logging for operations
audit_service.py Audit log writer for tracking user actions

Route Organization

Routes are organized into Flask blueprints, each registered in routes/__init__.py. Each blueprint handles a specific domain:

Blueprint Routes
pages.py HTML page endpoints (/explorer, /git, /settings, etc.)
objects.py Object CRUD (/api/objects, /api/delete-objects, /api/clone-objects)
staging.py Staging operations (/api/staging, /api/staging/apply, /api/staging/undo)
files.py File/folder operations (/api/files, /api/folders)
git.py Git integration (/api/git/status, /api/git/commit)
bulk_ops.py Bulk rename and move (/api/apply-rename, /api/move-objects)
backups.py Backup management (/api/backups)
analysis.py Dependencies, inheritance, smart grouping
validation.py Config reload, validation, health checks
settings.py App settings, logging config, audit log
